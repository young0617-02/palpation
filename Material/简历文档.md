## 四、项目经历

### edge-ai-agent-gateway · 边云协同 AI Agent 网关

**角色**：独立开发者（方案设计、编码、测试、部署、文档全流程，共 16 次提交）　
**技术栈**：Python 3.12 / FastAPI / pydantic v2 / paho-mqtt / onnxruntime / llama-cpp-python / SQLAlchemy / Prometheus / Docker / uv

#### 4.1 项目背景与目标

工业现场若把全部智能放在云端，会同时撞上三堵墙：毫秒级联锁等不起网络往返、厂区断网是常态而非异常、10kHz 原始振动数据全量上传既昂贵又涉及数据出域。项目目标是在 **2 核 4G** 的边缘盒子上构建一个可离线自治的诊断 Agent：**断网时自主判断、联网后由云端持续进化，且原始数据一步不出厂**。围绕该目标实现了「多协议采集 — 四级推理 — 本地知识诊断 — 断网自治 — 云端深度诊断 — 模型灰度下发」的完整闭环。

#### 4.2 我的职责

独立设计并开发全部 5 个模块（实测规模）：

| --- | --- | --- |
| `edge/` | 边缘网关：多协议采集、流处理、端侧 Agent、离线队列、资源护栏、云边协同 | 5087 行 |
| `cloud/` | 云端服务：设备注册、深度诊断、模型工厂、灰度 / 影子 / 回滚 | 2866 行 |

#### 4.3 技术亮点

1. **端云协同四级推理流水线，告警路径与 LLM 路径异步解耦**
   将边缘推理拆为 T1 确定性规则、T2 ONNX 异常检测、T3 端侧 LLM 语义初判、T4 本地知识检索四条路径。**难点**在于「既要 <50ms 确定性告警、又要带语义初判」，单一串行链路上二者会互相拖累。**解法**是把 T1/T2 告警与 T3 LLM 初判置于两条独立异步链路：规则命中即发事件，LLM 初判作为旁路结果追加到同一事件，告警**永不等待大模型**——两个指标各自达标、互不阻塞。

2. **端侧 LLM 工程化：从"跑起来"到"输出可解析"（修复 JSON 解析率 0% → 100%）**
   基于 llama-cpp-python 加载 Qwen2.5-0.5B GGUF 量化模型，在 ≤32 token 短输出约束下做结构化 JSON 初判。**难点**是初版解析率恒为 0%、推理静默降级到规则兜底。**定位与解法**：确认根因是 `infer` 使用 completion 接口、未套用 Instruct 模型的 chat template，导致模型只复述 prompt；同时 prompt 中的字段示例形似 set 简写，诱导非标准 JSON。改为 `create_chat_completion` 套用对话模板、改写标准 JSON 示例，并为 `_parse_json` 增加轻量容错（去尾逗号、单引号转双引号）。修复后真实模型实测 **parse_rate 0.000 → 1.000（20/20）**，并补充真实推理集成测试防回归。

3. **ONNX 判别式模型部署与多级降级链路**
   以 onnxruntime 承载轻量异常检测模型（CPU 端算子稳定、一套模型多端可跑）。**难点**是边缘内存与算力随负载波动，推理组件不能成为单点。**解法**是构建「T2 完整模型 → 简化 Z-Score → 规则兜底」的多级降级链路，任一级不可用时自动下沉到下一级，保证告警能力始终在线，并在事件上显式标注降级状态。

4. **2C4G 约束下的资源治理：降级矩阵 + cgroup 硬限**
   依据内存峰值、磁盘余量、CPU 温度等指标，在 `normal / llm_small / llm_off` 档位间切换端侧能力，配置代码化落地为资源护栏模块；配合 docker-compose 的 `cpus=2.0 / mem_limit=4g` 与 read-only 根文件系统、cap_drop 能力裁剪，将大模型对采集告警链路的资源挤占风险前置隔离。

5. **可靠性工程与 MLOps 闭环**
   断网期事件写入 SQLite 本地队列（本地权威、append-only 审计），恢复后按**水位线**顺序批量补传，以 `event_id` 唯一索引做**幂等去重**、以 `(gw_id, seq)` 做缺口检测；云端侧实现模型工厂、**环形灰度发布**、**影子验证**（新模型并行推理只记录不生效）与探针失败**自动回滚**，模型 / 固件 / 配置三层版本解耦，回滚在秒级完成（设计目标，探针失败即触发 `OtaEngine.apply()` 内的槽位自动回滚 `slots.rollback()`）。
